## Part 1

> What does a Deployment give you that a bare Pod doesn't? Why do we need a separate Service object instead of talking to a Pod's IP directly?

A pod is a single object with nothing watching it, so if it gets deleted or its node fails, it will stay gone. A Deployment is a controller holding a desired state which is reconciled continuously by a control loop. It creates a ReplicaSet which compares the number of pods matching its selector against the desired replicas and creates pods from a fixed pod template when there are too few or deletes them when too many, so pods come back on their own after a crash or a node failure. It also makes scaling just a matter of changing replicas. Editing the pod template creates a new ReplicaSet, and the Deployment shifts replicas from the old one to the new one incrementally, bounded by maxSurge and maxUnavailable so the app stays available throughout. The old ReplicaSet is kept at zero replicas, which is what kubectl rollout undo scales back up.

A Service is needed because a pod's IP is assigned when the pod is created but is deleted when that pod dies. Since pods are disposable, after a crash or a rollout, you get a different pod at a different address, so anything holding the old IP is left pointing at nothing. A service has its own virtual IP and DNS name that last as long as the Service does, and it picks its backends by label rather than address. The endpoints controller keeps that set current as pods come and go, and kube-proxy load balances across the ones that are ready. This is why webui-deployment.yaml sets OLLAMA_BASE_URL to http://ollama:11434 rather than a pod IP, as naming the service means the frontend will keep working through Ollama restarts without actually changing configs. 

## Part 2

> What is a Helm chart, and how do `values.yaml` plus `-f`/`--set` let the same chart produce different Kubernetes resources for different environments? Why is this better than keeping separate copies of your Part 1 manifests for staging and production?

A helm chart is a packaged Kubernetes application with a directory holding Chart.yaml with the chart's name and version, a templates directory of manifests written as Go templates, and values.yaml holding the default configuration. Installing a chart creates a release, a named and versioned instance of that chart. The templating is resolved before reaching Kubernetes, so API servers only see plain manifests and would never know the chart even existed. 

The templates don't hardcode names, limits, or images, and instead reference .Values and .Release.Name. At install time, Helm merges the values in precedence order, starting with values.yaml. Then, each file is passed with -f and anything given with --set, which merges key by key so an override only specifies what differs. Rendering the same templates against different merged values will produce different results, which is why values-staging.yaml gives a 2Gi volume and the qwen2.5:0.5b model while values-production.yaml gives a 5Gi volume, higher CPU and memory limits, and qwen2.5:1.5b. Prefixing every object name with the release name is what lets the two installs coexist, as ollama-staging-ollama and ollama-production-ollama.

Keeping one chart is better than keeping two copies of the Part 1 manifests because the structure only lives in one place. With copied directories every structural change has to be made twice by hand, and missing one lets staging and production drift apart silently, which makes staging useless as a rehearsal for production. The two values files are also the diff, so the few real differences between the environments are stated in a few lines instead of being buried in a hundred identical ones. Helm also tracks each release separately, so helm upgrade and helm rollback act on one environment at a time and upgrading staging cannot affect production, while kubectl apply against a copied folder has no revisions to roll back to at all. The chart also carries lifecycle work that the manifests could not, as the model pull that was a manual kubectl exec in Part 1 is now a post-install and post-upgrade hook Job that runs on every fresh install. Standing up a third environment is then just one more values file instead of another copy to keep in sync.
